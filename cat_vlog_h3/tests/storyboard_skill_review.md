# 小猫编剧 Skill 本地人工情景走查

日期：2026-10-07。以下是同一作者依据完成的 Skill 进行的对话情景走查，记录实际拟定的响应与检查结论；不是独立模型评测、自动触发成功率或 GPU 画质测试。自动化部分另见 `test_storyboard_skill.py`。

## 只有大学生活的几个场景

输入：「帮我写小猫大学生活 Vlog。我想到起床、赶课、食堂、图书馆，其他还没想好。」

首轮拟定响应：已有地点和一天的顺序，但还缺小猫遭遇的具体事件。邀请用户先说：这期主要给在校生还是怀念大学的人看、希望留下什么感觉；四个场景中有没有一个尴尬／委屈／开心的真实细节最想保留；是否接受默认轻度拟人。这轮不直接套出十个镜头，也不要求用户填模型字段。

走查结论：问题来自信息缺口，三个问题覆盖受众情绪、素材和拟人边界；下一轮沿用户选中的片段深化，而非再次询问同一清单。

## 完整草稿但有重复

输入条件：用户已明确在校生观众、轻度拟人、无对白，给出十镜；第 3 镜上课睡觉和第 6 镜图书馆睡觉表达相同疲倦，最后拿鱼干送给朋友但没有铺垫。

拟定响应：直接评审两次睡觉的信息重复，建议保留其中更能承接故事的一次，把另一镜改为「很困却努力让出／守住一个与主线有关的位置」等具体选择，再依据用户原主线选定，而非硬套同一个校园笑话。结尾的分享需要前文出现鱼干或朋友关系，指出该关联并修订对应镜头。已知观众和拟人程度无需再问。

走查结论：严格审的是场景作用，改法保留疲倦或友情的情绪核心；第 6 镜变化要联查结尾，不能只孤立替换提示词。

## 十二个候选，同时希望四秒短镜

输入：「这十二个都不错，赶课只要四秒，食堂可以九秒，直接导入现有工作流。」

拟定响应：说明现有执行图固定十镜、每镜约 7.29 秒，JSON 秒数字段不会控制时长。对十二个候选按重复度、开场作用和结尾联系精选十个，另外两个列作备选；若用户坚持新数量或时长，将工作流修改作为单独任务，而非假装当前 Skill 已支持。

走查结论：执行 JSON 不出现第十一镜或 `duration_seconds`。对应 CLI 负例已覆盖十二镜和不受支持的时长字段。

## 定稿和计划模式

输入：「场景都定了，把完整 JSON 给我，我还在计划模式。」

拟定响应：提供符合字段约定的完整 JSON 草稿，补齐十镜首帧、动作终点、声音和禁止条件；不称已保存文件，不借 Skill 切换模式。允许写文件后再保存并运行真实项目校验，检查二十条组合提示词中的具体机位、场景、动作和声音。发布文案与导演评语放在 JSON 之外。

走查结论：计划模式边界与交付方式明确。现有雨天示例只用于真实校验器的结构集成测试，不宣称它已经达到新 Skill 的开场创意标准；钩子强弱、共鸣和视频可达性仍需人工审稿及后续样片反馈。

## v3 原生声画与角色适配（2026-10-07）

通用接口改为 characters／cast／audio；静音、环境声、对白、两人轮流说话、画外音、演唱和配乐通过同一个组合器测试。旧稿中的“无对白”只代表该情景给定偏好，不是 Skill 的全局限制。舞蹈面试稿已保留原中文台词并结构化，音乐由 H3 原生生成；未做独立模型行为评测或 GPU 推理。
